# AGENTS.md

Guidelines for coding agents (and people) who change Herdling.
Read this file before you change code.

## 1. The project

Herdling is a phone app for [herdr](https://herdr.dev), the terminal workspace for AI coding agents.
It shows the agents on the user's own computers, sends a push when an agent finishes or needs the
user, and lets the user answer from the phone. License: MPL-2.0. Owner: Zog Tech, Inc.
Website: https://herdling.zog-tech.com. Contact: admin@zog-tech.com.

| Part | Path | What it is |
|---|---|---|
| App | `app/` | Expo SDK 58 app for iOS and Android (Expo Router, TypeScript, React 19.3, React Compiler on) |
| Native modules | `app/modules/` | Local Expo modules in Swift and Kotlin: `ssh`, `voice`, `paste` |
| Companion | `companion/` | `herdlingd`, one Rust binary per computer (macOS and Linux) |
| Protocol | `protocol/` | Shared TypeScript types for the RPC (`@herdling/protocol`) |
| Docs | `docs/` | `protocol.md`, `voice.md`, design specs and plans in `superpowers/` |
| Design system | `design-system/herdling/` | `MASTER.md` and per-screen pages |
| Website | `site/` | The public website |
| Store | `store/` | App Store and Google Play listing text |

Rules for every change:

- **Every feature works on iOS and Android**, or the app shows a clear message where it cannot.
- **An old app and a new `herdlingd` work together, and the reverse.** Follow the compatibility
  rules in `docs/protocol.md`: add methods and fields only, never rename or remove them, make new
  fields optional, and check `hello.methods` before you use a new method.
- **No Zog Tech server.** Session traffic goes only between the phone and the user's computers
  over SSH. Do not add analytics, accounts or a relay.

## 2. Commands

Use pnpm 10, not npm or yarn. Node 22 or later. Rust stable.

| Where | Command | What it does |
|---|---|---|
| root | `pnpm install` | Installs the workspace (`app`, `protocol`). `node-linker=hoisted` (`.npmrc`) |
| `app/` | `pnpm exec tsc --noEmit` | Type check |
| `app/` | `pnpm test` | All Jest tests (`jest-expo` preset) |
| `app/` | `pnpm jest src/board` | Jest tests under one path |
| `app/` | `pnpm start` | Metro for an installed development build |
| `app/` | `pnpm expo run:ios`, `pnpm expo run:android` | Builds and runs the development client |
| `protocol/` | `pnpm exec tsc --noEmit` | Type check |
| `companion/` | `cargo clippy --all-targets -- -D warnings` | Rust lint (must be clean) |
| `companion/` | `cargo test` | Rust tests |
| `companion/` | `cargo build --release` | The release binary in `target/release/herdlingd` |

CI (`.github/workflows/ci.yml`) runs the type checks, the Jest tests, clippy and `cargo test` on Linux.
The companion code is not formatted with `rustfmt` yet, so CI does not run `cargo fmt --check`.
Do not run `cargo fmt` over the whole crate in a feature change: it makes a large diff.

`app/ios/` and `app/android/` are generated by prebuild (Expo CNG). They are not in git.
Never edit them by hand: change `app/app.json`, a config plugin or `app/modules/` instead.

The app does not run in Expo Go. To try it with no computer, open `herdling://demo` (the demo host
in `app/src/demo/`).

## 3. Architecture map

```
Phone app ──SSH (restricted key, command="herdlingd rpc")──▶ herdlingd rpc ──▶ herdr socket
                                                             herdlingd serve ──▶ Expo push
```

### App (`app/src/`)

The path alias `@/` points to `app/src/`.

| Path | Responsibility |
|---|---|
| `app/` | Expo Router routes: tabs, session, subagent, new session, pairing, host screens, `demo` |
| `rpc/` | `RpcClient`: request ids, responses, streamed events, cancel |
| `hosts/` | Saved computers, the connection manager, discovery, password setup, `methods.ts` (`APP_METHODS`) |
| `pairing/` | Pairing by code and QR code, the pairing URL |
| `herdr/` | herdr snapshot, start, restart, resume, rename and close actions |
| `board/` | The board: buckets, rows, the peek sheet, elapsed clocks |
| `thread/` | The chat view: thread items, follow, composer, permission choices |
| `terminal/` | The ANSI terminal view and the key row |
| `push/` | Push token, registration with each computer, notification routing |
| `voice/` | Recording, recognition, speech, summaries |
| `usage/`, `automations/` | Plan usage meters and the automations tab |
| `theme/`, `ui/` | Design tokens (`theme/tokens.ts`) and shared UI parts |
| `demo/` | The demo host and its scripted scenario |

### Companion (`companion/src/`)

| Path | Responsibility |
|---|---|
| `main.rs` | Subcommands: `rpc`, `serve`, `pair`, `enroll`, `install [--dry-run]`, `update`, `version` |
| `rpc.rs` | The RPC loop and `METHODS` (must match the dispatch; a test checks it) |
| `herdr.rs`, `events.rs` | The herdr socket client and event subscription |
| `claude/`, `transcript/` | Claude Code log parsing, and the adapters for Codex, Pi and OpenCode |
| `serve/` | The user service: herdr watch, push debounce, desk activity ("quiet at the computer"), Bonjour, the pairing HTTP endpoint |
| `pair.rs`, `enroll.rs` | Pairing window, code checks and the `authorized_keys` line |
| `install.rs` | launchd agent (`com.zogtech.herdlingd`) or systemd user unit |
| `git.rs` | Read-only git views (`git.status`, `git.diff`) and `git.worktree_add` |
| `update.rs` | Self-update from the GitHub release: `update.check`, `update.apply`, `herdlingd update` |
| `push.rs` | Expo push messages. Never log push tokens |
| `stt.rs`, `tts.rs`, `summary.rs`, `hostcmd.rs` | Optional host commands from `~/.config/herdling/config.toml` |
| `stats.rs`, `usage.rs`, `automations.rs` | Host stats, plan usage, the `herdr-automate` adapter |

When you add an RPC method, add it to `METHODS` in `companion/src/rpc.rs`, to `APP_METHODS` in
`app/src/hosts/methods.ts`, and to the types in `protocol/src/index.ts`. Document it in `docs/protocol.md`.

## 4. Code conventions

- **Comments explain why.** Each module starts with a short doc comment that says what it is for.
- **Pure core, thin I/O.** Put rules in pure modules and test them. Pass I/O in as parameters
  (the install `Runner` trait, the demo transport).
- **Design system.** Use the tokens from `app/src/theme/` and the rules in
  `design-system/herdling/MASTER.md`. Never put a raw color or size in a style. Gold is only for
  the primary action, the working state and the selected state.
- **Security.** Every input that ends up in `authorized_keys` is validated in `pair.rs`. The phone
  key line forces `command="<exe> rpc"` and turns off forwarding and the PTY. Do not weaken this.
  Never log push tokens, keys, pairing codes or passwords.
- **TypeScript** `strict`, no `any`. **Rust**: clippy clean with `-D warnings`.
- **Tests.** App tests sit next to the code (`*.test.ts`, `*.test.tsx`). Companion tests are in
  `companion/tests/`. Add or update a test when you fix a bug or add logic.
- **Dependencies.** Do not add one without a reason. A native dependency forces a native build.

### Writing style

Write comments, docs, commit messages and user-facing text in ASD-STE100 Simplified Technical English:

- Active voice, present tense. One instruction per sentence.
- At most about 20 words in an instruction and 25 words in a description.
- Use the same term for the same thing every time. No idioms and no slang.
- Use articles ("the", "a"). No noun clusters of more than 3 words.

## 5. Native build or over-the-air update

The app ships JavaScript in two ways: a native build (store or TestFlight), or an over-the-air
(OTA) update with `expo-updates`. An OTA update takes seconds; a native build takes much longer
and needs a store review.

**A change needs a native build when it touches:**

- `app/modules/**` (Swift, Kotlin, podspecs, Gradle files, `expo-module.config.json`).
- A dependency with native code: added, removed or upgraded (`expo-*`, `react-native-*`).
- `app/app.json` native config: `ios`, `android`, `plugins`, permissions, `infoPlist`, icons,
  splash, `scheme`.
- The Expo SDK or the React Native version.

**A JS-only change ships as an OTA update:** code in `app/src/`, assets that Metro bundles and
JS-only dependencies.

**Rules:**

- `runtimeVersion` uses the `appVersion` policy. All binaries with the same `version` in
  `app/app.json` get the same OTA updates. **Never bump `version` in `app/app.json`.** A new
  `version` cuts every installed binary off from new updates. Only the maintainer decides on a
  version change. EAS sets the build number (`appVersionSource: remote`).
- Old binaries get new JS. **New JS must not need a native module that older binaries lack.**
  Load a new native module lazily and handle its absence (see the photo picker and the document picker in `thread/attachments.ts`, which load only on use).
- Before an OTA update, compare the native dependencies and plugins with the oldest build still
  in use (`docs/protocol.md`, "Before an OTA update").
- EAS profiles (`app/eas.json`): `development`, `preview`, `production`. Each has its own channel.

## 6. herdlingd on the user's computers

- `herdlingd install` copies the running binary to `~/.local/bin/herdlingd` and registers the user
  service (launchd on macOS, systemd user unit on Linux). On a reinstall it restarts the service.
- To deploy a new `herdlingd` to a computer: build it there (or for its target) with
  `cargo build --release`, then run `./target/release/herdlingd install`. The next SSH channel
  runs the new `rpc` code; the service restarts with the new `serve` code.
- Users get `herdlingd` from the GitHub release: the app ("Install and pair"), the installer
  `site/public/install.sh`, or `update.apply` / `herdlingd update`. The spec with the trust model is
  `docs/superpowers/specs/2026-10-31-herdlingd-install-update-design.md`.
- The installer's `--quiet` lines (`HERDLINGD_STEP`, `HERDLINGD_INSTALLED`, `HERDLINGD_ERROR`) are a
  contract with `app/src/hosts/installer.ts`. The release asset names and `latest.json` are a
  contract with `companion/src/update.rs` and the installer. Do not rename them.
- The phone key runs `~/.local/bin/herdlingd rpc`. Do not move the binary without an update of
  the `authorized_keys` lines.
- A new `herdlingd` must keep working with the app builds that people use (section 1).
- The one-line installer needs a herdlingd release. Until the first release, the docs say
  "after the first release" and `installer.ready` is `false` in `site/public/config.js`.

### Releasing herdlingd

Only the maintainer releases. The steps are in `CONTRIBUTING.md` ("Releasing herdlingd"):
bump `version` in `companion/Cargo.toml`, update `CHANGELOG.md`, tag `herdlingd-vX.Y.Z` and push the
tag. `.github/workflows/release-herdlingd.yml` builds the four targets and publishes the release.
Installed apps and `herdlingd` find it through the "latest" release.

## 7. Builds on a shared machine

The build machine is shared and has a small internal disk. Keep builds light:

- Run heavy commands with a low priority: `nice -n 15`.
- Run one heavy build at a time (a native app build, a Gradle build or a release `cargo build`).
  Check for running builds first, for example `pgrep -fl "eas build|gradle|xcodebuild"`.
- Cap Gradle: `--max-workers=2` and a JVM heap of about 4 GB. Stop the Gradle daemon after the build.
  Limit Jest with `--maxWorkers=2` and Cargo with `-j 2`.
- Put build output, caches and derived data on the external build volume, not on the internal disk.
  Delete the build folder after the build.

## 8. Privacy and Git

- This repository is meant to become public. Never commit secrets, keys, tokens, `.env` files,
  signing files, personal names, personal email addresses, host names, IP addresses, home folder
  paths, SSH aliases or the names of other private projects.
- Use generic data in tests and docs: users "sam" or "demo", hosts such as `studio.local`, paths such
  as `/home/sam/proj`, and documentation IP ranges.
- Commits use the project identity `zog-tech`. Check `git config user.name` and `git config user.email`
  before you commit.
- Commit message: an area prefix and one short line, no period, no `feat:` prefix, under about 72
  characters (`board: …`, `companion: …`, `app: …`). Then a blank line and the reason.
- Make small, focused commits. Work on a branch from `main`. Put agent worktrees only in
  `.claude/worktrees/<name>` (it is in `.gitignore`).
- Update `README.md`, `docs/` and `CHANGELOG.md` when a change alters what the app or `herdlingd` does.
- Do not push, release, publish an OTA update, submit to a store or deploy the site unless the
  maintainer asks.
